# Whop Business Snapshots — DRF Productisation Channel

**Status:** Active opportunity  
**Research date:** 29 August 2026  
**Governing issue:** #8

## Decision

DRF should treat **Whop as a standing productisation and distribution channel**.

When normal operations produce a useful, repeatable business asset, DRF should ask:

> Can this be sanitised, packaged and sold as a reusable snapshot, template, setup, operating system, workflow, automation, toolkit or implementation pack?

The objective is not to manufacture low-value digital products for the sake of having products. The objective is to **harvest proven operating work that DRF is already creating**, remove client/private data, package the reusable layer, and create an additional revenue stream from the same work.

This creates a flywheel:

```text
operate a real business
→ discover something useful
→ prove it internally
→ extract the reusable layer
→ sanitise and package
→ list on Whop
→ sell
→ learn from buyers
→ improve the operating asset
→ create more value internally and externally
```

## What was verified

### 1. Snapshot-style products are already being distributed on Whop

Public Whop marketplace listings explicitly use snapshot positioning.

Examples:

- **Artist Template** — marketed as **“Copy This Snapshot — Run Your Entire Tattoo Business on Whop.”**  
  Source: https://whop.com/discover/guest-spot/artist-template/
- **Studio Template** — marketed as **“Copy This Snapshot — Run Your Entire Tattoo Shop on Whop.”**  
  Source: https://whop.com/discover/guest-spot/studio-template/
- **GHL AI Agency** — a seller advertises AI systems previously sold for $10,000+ as a **snapshot for $497**.  
  Source: https://whop.com/discover/ghl-ai-agency/ghl-ai-agency/
- **The Snapshot Marketplace** sells individual snapshots and a bundled access offer.  
  Source: https://whop.com/the-snapshot-marketplace/lifetime-all-access-pass/

This validates the broader commercial behaviour David identified: reusable business configurations and operating systems can be productised and sold through Whop.

### 2. Whop is intentionally built for digital-product monetisation

Whop publicly positions itself as a platform for selling digital products such as templates, software, courses, memberships, AI-driven products and services.

Whop also supports one-time and recurring products, product delivery, access control, analytics and marketplace discovery.

Sources:

- https://whop.com/blog/how-to-sell-digital-products/
- https://whop.com/blog/selling-digital-products/
- https://whop.com/blog/best-place-to-sell-digital-products/
- https://whop.com/blog/subscription-billing-software/

### 3. The current public evidence does not clearly establish a separately documented Whop platform feature formally named “Business Snapshots”

The public marketplace clearly shows **copyable snapshot/template offers**, but current indexed Whop documentation does not expose a definitive product-documentation page for a formal platform primitive called **Business Snapshots**.

Therefore DRF should distinguish between:

1. **Verified commercial model:** selling/copying packaged business snapshots and templates through Whop.
2. **Potential newly released Whop UI feature:** if the current Whop dashboard labels this capability “Business Snapshots”, document its exact UI mechanics once directly observed in the account.

This distinction prevents us from overstating what has been independently verified.

## Why this fits DRF

DRF already exists to repeatedly discover, validate and operationalise revenue-producing methods. That naturally creates sellable intellectual property.

The marginal cost of productising a proven DRF asset can be low because the expensive part — discovery, research, testing and operating refinement — was already required for the underlying business.

The opportunity is therefore **secondary monetisation of proven operational IP**.

### Core principle

**Do not build for Whop first. Operate first. Productise proven residue.**

This preserves the DRF root rule:

> Traction before build. Revenue work before optional build work.

## Product qualification gate

Do not list every internal artifact. A candidate should pass most of these tests.

| Test | Question |
|---|---|
| Proven | Has it actually been used or validated? |
| Repeatable | Can another operator reproduce the outcome? |
| Transferable | Can it work outside the exact originating business? |
| Valuable | Does it save meaningful time, money, uncertainty or implementation effort? |
| Sanitised | Can all customer, candidate, credential and proprietary third-party data be removed? |
| Explainable | Can the buyer understand what it does and how to deploy it? |
| Maintainable | Can DRF reasonably support/update it if required? |
| Differentiated | Is it more useful than a generic prompt/template available free online? |
| Sellable | Is there an identifiable buyer with an existing problem? |

A practical rule:

> **If it has not created measurable value for us, do not call it a proven snapshot.**

## Packaging standard

Each DRF snapshot should be a **clean product**, not a dump of internal files.

Minimum package:

```text
01 - START HERE
02 - WHAT THIS SOLVES
03 - SNAPSHOT / TEMPLATE / SETUP
04 - INSTALL OR IMPORT GUIDE
05 - OPERATING GUIDE
06 - EXAMPLE / DEMO
07 - CUSTOMISATION POINTS
08 - VERSION + CHANGELOG
09 - SUPPORT / LIMITATIONS
10 - LICENCE
```

Where the product is directly importable into another system, the importable artifact is the core deliverable and the documentation should remain short.

## DRF harvesting workflow

```text
1. DISCOVER
   A useful system emerges from real DRF/Talent Bridge/iMPLEMENTAi work.

2. PROVE
   Confirm it works in a real operating context.

3. NOMINATE
   Mark it as a potential Whop product candidate.

4. EXTRACT
   Separate reusable logic from company/client-specific implementation.

5. SANITISE
   Remove secrets, personal data, client data, candidate data, internal URLs,
   credentials, licences and third-party material we do not have rights to resell.

6. PACKAGE
   Convert it into a buyer-ready snapshot/setup/template/toolkit.

7. QA
   Test deployment from a clean environment/account where practical.

8. PRICE
   Price against buyer value and implementation time saved — not file count.

9. LIST
   Publish on Whop with a clear problem, outcome, contents, requirements and limitations.

10. MEASURE
    Track views, conversions, refunds, support burden, revenue and buyer feedback.

11. IMPROVE OR KILL
    Improve products with traction. Retire products that create support burden without revenue.
```

## Pricing hypothesis

Do not lock pricing globally. Test by value class.

### Entry products

Examples: checklists, templates, small prompt packs, simple calculators.

**Indicative test range:** $9–$49 one-time.

### Operating packs

Examples: complete workflow packs, role-specific systems, agent setups, repository starters, automation kits.

**Indicative test range:** $49–$299 one-time.

### Business snapshots

Examples: proven niche operating systems, HighLevel snapshots, complete launch/CRM/automation configurations.

**Indicative test range:** $199–$999+ one-time depending on proven value and deployment depth.

### Product + implementation

Whop can also act as the entry point into higher-value services:

```text
snapshot purchase
→ optional setup service
→ custom implementation
→ managed service
→ consulting / optimisation
```

This makes the snapshot both a revenue product and a qualified lead generator.

## Important risks and controls

### Intellectual property

Whop prohibits infringing/counterfeit goods and unauthorised proprietary material. Only sell assets DRF/iMPLEMENTAi/Talent Bridge owns or is expressly licensed to redistribute.

Source: https://whop.com/prohibited-products-and-services/

### Private and customer data

Never include:

- customer records;
- candidate records;
- personal information;
- passwords;
- API keys;
- OAuth tokens;
- secrets;
- private URLs;
- payment data;
- proprietary client material.

Use synthetic examples where examples are required.

### Third-party subscriptions and licences

A snapshot must not imply that paid third-party software, subscriptions, models, themes, plugins, APIs or content are included unless redistribution rights expressly permit it.

### Earnings claims

Do not market a snapshot using unsupported income claims. State the proven operational outcome precisely and separate historic results from guarantees.

### Platform dependence

A product dependent on Whop, HighLevel, GitHub, ChatGPT, Claude or another platform may break when the platform changes. Version products and disclose dependencies.

### Support burden

A $29 product that produces hours of support is a bad product. Track **net contribution after support**, not gross sales alone.

## Measurement

Each product should track at minimum:

- launch date;
- price;
- units sold;
- gross revenue;
- refunds/chargebacks;
- support time;
- net contribution;
- conversion rate where available;
- implementation/custom-service leads generated;
- version/update burden;
- buyer feedback;
- keep/improve/retire decision.

## Standing DRF rule

From now on, when a reusable asset emerges during DRF operations, ask:

> **Is this a Whop product candidate?**

If yes, do not interrupt the core operating work. Record the candidate, finish proving the underlying system, then productise the reusable layer.

## Immediate next step

Do **not** build a large Whop catalogue yet.

Select the first **one to three assets that are already substantially proven**, package the simplest one, list it, and use actual buyer behaviour to validate the channel before scaling production.

This preserves KISSS and prevents DRF from creating a new speculative content factory instead of a revenue factory.
